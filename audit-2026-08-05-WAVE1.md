## PERFORMANCE — this answers the 3.12 it/s question

**[critical] Full-covariance KL runs unconditionally in float64.**
`FullGaussian.renyi_closed_form` sets `compute_dtype = torch.float64` with no toggle
(`vfe3/families/gaussian.py:~600-607`) — unlike the `result_dtype` line directly above it, and unlike
`DiagonalGaussian.renyi_closed_form` (`gaussian.py:210-274`) which upcasts only inside a narrow
cancellation guard. `_factored_full_covariance` (`vfe3/geometry/transport.py:2811-2827`) likewise
forces `exp_phi`/`exp_neg`/`sigma_blocks` to double. So the self term `(48,64,20,20)` = 3,072
matrices and the pairwise term `(48,64,64,20,20)` = 196,608 matrices run cholesky + two
`solve_triangular` + logdet entirely in fp64. Consumer Blackwell (RTX 5090) has crippled fp64
throughput. **Compute-bound on the fp64 unit, not memory-bound — exactly why 6GB/32GB coexists with
3.12 it/s.** Corollary: raising batch/seq makes it WORSE, since cost is O(B*N^2) fp64 op count, not
bytes. `nvidia-smi` during the live run showed 91% util / 6131 MiB.
Fix direction: reuse the project's existing escalate-on-failure seam (`stable_matrix_exp_pair`'s
`exp_fp64_mode='norm'`) — fp32 default, upcast only pairs that fail a conditioning check. Numerics-
changing, so it must be gated behind a new toggle.

**[high] `safe_cholesky(rounds=5)` forces a device-to-host sync on every call.**
`vfe3/numerics.py:222-224` evaluates `bool(ok.all())` unconditionally whenever `rounds > 0`. Called
with `rounds=5` from `gaussian.py:622-623,645-647` and `prior_bank.py:1142`, plus `_certify_public_spd`
(`retraction.py:357,419`) — **at least 5 forced syncs per training step**, draining the launch queue on
a workload whose per-launch GPU work is tiny. `prior_bank.py:1138-1139` documents that the retry
branch never engages on the pure path, so `rounds=0` is byte-identical there and removes the sync via
short-circuit.

**[high] `oracle_unroll_grad=True` triples the fp64 traversal.**
`e_step.py:1109` -> `oracle.py:230 create_graph=use_live` keeps the E-step gradient graph-attached, so
the outer `loss.backward()` differentiates the fp64 cholesky chain a second time (~3x total).
**Not a defect** — it is the documented mechanism letting the unrolled E-step reach `phi_embed`.
Report as measured headroom, not a bug.

**[medium] Redundant `eigh` in `retract_spd_full`.**
`retraction.py:505-514` calls `_symmetric_spectral_map` twice on the IDENTICAL `sigma` (`sqrt_floor`
then `inv_sqrt_floor`), i.e. two full `eigh` over `(3072,20,20)` where one shared eigendecomposition
serves both. Bit-identical dedup available.

## THE F-ASCENT MECHANISM — with an executed repro

**[critical] `gaussian_full` saturates the `kl_max` clamp ~5x earlier in phi than `gaussian_diagonal`,
freezing the coupling gradient to exactly zero.**
Locations: `vfe3/geometry/transport.py:2424-2437` (dense congruence),
`vfe3/families/gaussian.py:503-524` (`FullGaussian.transport_dispersion`), `kl_max = 8*K = 160`.

Measured, both families given the same diagonal covariance so only the family differs:

```
phi_scale=0.06   diag F0=1.359  d=-1.38e-02  |  full F0=5.843  d=-2.44e-02
phi_scale=0.20   diag F0=15.62  d=-7.03e-03  |  full F0=32.57  d=-8.24e-04
phi_scale=0.30   diag F0=28.28  d=-1.33e-03  |  full F0=33.27  d=+0.00e+00   <- EXACTLY frozen
phi_scale=0.50   diag F0=33.13  d=-1.91e-05  |  full F0=33.27  d=+0.00e+00
```

Mechanism: the diagonal path's truncation `sum_l Omega_kl^2 sigma_l` is an implicit bounded-sum-of-
squares regularizer. The full congruence has `cond(Omega)^2` blow-up and never applies it, so it hits
`safe_kl_clamp`'s zero-derivative ceiling far earlier. Once the coupling term freezes, the M-step
keeps pushing `phi_embed` deeper into saturation via CE alone — a run that trains to completion while
the belief-coupling term is permanently inert.

This **contradicts** the wiki claim that `gaussian_full` "avoids the question entirely by carrying the
whole covariance": it is MORE exposed than diagonal, not immune.

Caveat: the repro used the train_vfe3 knobs (see config correction). Re-run under the ablation values
(`fisher` precond, `e_mu_q_trust=None`, `e_q_mu_lr=0.4`) before treating the numbers as ablation-exact.

**[medium] The fail-closed guard for exactly this blow-up is never engaged.**
`transport_chart_max_norm` / `validity_max_norm` (`e_step.py:89`) exists to fail closed rather than
silently saturate, and neither driver ever sets it (default `None`).

**[high — INERT on ablation, LIVE on train_vfe3] Mean trust region box-clamps in the Cholesky basis.**
`apply_mu_trust_region`'s full branch (`numerics.py:167-184`) whitens with the asymmetric Cholesky
factor and box-clamps in that arbitrary basis, while `retract_spd_full` (`retraction.py:505-516`) uses
the symmetric eigenbasis sqrt in the same iteration. Measured rotation when it binds:
`cos(raw, box)=0.79` vs `cos(raw, ball)=1.00` vs `cos(raw, symmetric-box)=0.85`. The diagonal family
cannot exhibit this — its whitening basis IS the coordinate axes. Gated on `e_mu_q_trust is not None`.

## BLOCKED FEATURES

**[high] The closed-form kernel tier is structurally unreachable for `gaussian_full`, and cannot be
unlocked by registration.** `uses_kernel_route` (`gradients/kernels.py:298-309`) hardcodes
`family == "gaussian_diagonal"`; `_KERNELS` has exactly one entry; the trailing `has_kernel(family)` in
that predicate is dead weight, so `@register_kernel("gaussian_full")` would still leave it False.
`config.py:2812` therefore makes `e_step_update='mm_exact'` unconstructible under `gaussian_full`,
transitively blocking `emission_mode` (`config.py:1674`) and the mm_exact-only precision-split
diagnostics. Fix direction: declare a capability tuple on `register_kernel`, mirroring how
`register_decode` already declares `covariance_kinds` / `family_consistent`.

**[medium] The per-token prior has no off-diagonal capacity.** Under the default
`prior_source="token"`, `_encode_prior_sigma` (`prior_bank.py:1553-1567`) `diag_embed`-promotes the
prior; only the `model_channel` branch reads a packed strict-lower Cholesky table
(`s_sigma_lower_embed`). At L=1/T=1 the vocabulary's learned identity therefore carries ZERO
correlated-uncertainty capacity — `gaussian_full`'s namesake capability is largely inert on the
active path.

**[low] `compile_pair_kernel` is a silent no-op under `gaussian_full`** and is missing from
`config.py`'s own inert-knob coverage sweep (~`config.py:2958-3076`).
