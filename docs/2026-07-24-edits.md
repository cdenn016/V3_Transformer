# 2026-07-24 edits

## bf16 figures: widen the AMP -> analysis boundary

Under `amp_dtype='bf16'` five single-run figures died with
`TypeError: Got unsupported ScalarType BFloat16` (`belief_category_separation`, `belief_umap_mu`,
`belief_umap_sigma`, `sigma_stratified_error`, `sigma_ce_scatter`) while `belief_umap_phi` and the
model-channel panels rendered normally.

Root cause: `collect_inference_bank` captures the belief straight out of the autocast E-step, so
`out.mu` / `out.sigma` arrive in bf16 (`phi` survives because the gauge path keeps its own
autocast-disabled fp32 island, and the model channel comes from the fp32 encode-time prior). Those
bf16 tensors were CPU-hosted unchanged and reached the figure layer, where NumPy — which has no
bfloat16 dtype at all — cannot convert them. `model.build_diagnostic_snapshot` already upcasts at
exactly this boundary via `_freeze_tensor`; the viz bank capture was the one place that did not.

Three widening guards, all no-ops unless a reduced-precision float is present, so the
`amp_dtype=None` default path stays byte-identical:

- `vfe3/viz/extract.py` — new `_cpu_bank_tensor`, used by `_cpu_bank_value` for both the tensor and
  `CompactBlockElement` cases, widens bf16/fp16 to fp32 when hosting a bank field. This is the root-
  cause fix and the viz sibling of `model._freeze_tensor`. Integer and fp32 fields pass through
  untouched. bf16/fp16 -> fp32 is exact, so captured values are preserved.
- `vfe3/viz/figures.py` `_np` — widens bf16 before `.numpy()`, since that conversion is impossible
  for bfloat16 under any circumstance.
- `vfe3/viz/figures.py` `_belief_channel_features` — widens `sigma` before the log-Euclidean chart:
  `torch.linalg.eigh` has no bfloat16 kernel, so the full-covariance branch failed before the numpy
  boundary was even reached.

Tests: four added to `tests/test_amp.py` (bank-capture dtype, the `_np` boundary, both sigma
calibration figures rendering from a bf16 bank, and the belief-channel charts for diagonal and full
covariance). All four fail on the pre-fix tree with the reported `TypeError`.

Note for future runs: `_package_code_identity` hashes `ablation.py` and `train_vfe3.py`, so saving
either while pytest is running invalidates the guard mid-suite and fails every test that constructs
`RunArtifacts` afterwards. Verify against a stable source tree.
