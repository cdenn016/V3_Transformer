# 2026-07-27 edits

## Checkpoint save must not kill the run, `fix/2026-07-27-checkpoint-save-nonfatal`

A wikitext-103 K=210 run died at step 120000/180000 (10 h of GPU work) inside
`RunArtifacts.save_checkpoint`: `torch.save` raised `ios_base::badbit set: iostream stream error`
after writing exactly 2,663,051,456 bytes, then `PyTorchStreamWriter.__exit__` raised the
`unexpected pos 2663051584 vs 2663051456` cascade on top of it during unwind.

**Trigger: environmental, not identified.** Ruled out by measurement, not by argument -- NTFS
compression (a 3 GB `torch.save` into that same compressed `checkpoints/` dir succeeded; the
uncompressed control also succeeded, 14.5 s vs 1.3 s), hardware I/O error (clean `System` log
across the run window: no `disk`/`Ntfs`/`volsnap` events), and a compressed-file fragmentation
limit (the *successful* 5.2 GB `step_60000.pt` carries 30,650 extents against the failed file's
28,605). Disk-full is unconfirmed: 303 GB free, 15 GB in the recycle bin, no low-space events.
The same signature is reported upstream with no root cause in
[verl#3346](https://github.com/volcengine/verl/issues/3346),
[CellBender#301](https://github.com/broadinstitute/CellBender/issues/301) and
[lightning#21431](https://github.com/Lightning-AI/pytorch-lightning/issues/21431); torch here is a
dev nightly (`2.10.0.dev20251210+cu128`).

**Fixed, because the run loss is ours regardless of the trigger:**

`train.py` -- the periodic `save_checkpoint` call was the one unguarded I/O in a block whose every
other side effect (validation diagnostics, attention-map replay, figures) is deliberately
best-effort so "a viz/replay fault never kills training". A checkpoint is a convenience for
resuming, not a correctness requirement of the step loop, so it is now guarded the same way: warn
loudly, continue, let the next interval retry.

`run_artifacts.py` -- `_unique_sibling_temp` got exactly one `unlink` attempt and swallowed its
`OSError`, so the failed save abandoned a 2.48 GB `.step_120000.pt.<tag>.tmp` (freely deletable
minutes later -- it lost a race to the failed writer's still-open handle). Cleanup now retries on
the same 5x0.2 s backoff `_atomic_replace` already uses for Windows locks. Load-bearing now that a
failed save is non-fatal: otherwise each interval leaks multi-GB onto the disk the run is still
writing to.

`tests/test_checkpoint_save_resilience_20260727.py` -- +2 tests, both failing before the change.

Not changed: `checkpoint_interval` (60000 steps, which is what made the loss 60k steps rather than
one interval) -- config is the user's call.

**CPU lane** (`run_cpu_tests.py` under `C:/Python314`, the interpreter that carries `pytest-xdist`):
fast `tests=4445 failures=0 errors=0 skipped=28`. The slow lane's single failure,
`test_report.py::test_finalize_skips_figures_when_disabled` (`best-model finalization requires a
bound validation-data identity`), reproduces identically on pristine `main` and is not from this
change.

Two lane notes worth keeping, neither of them a regression: the suite cannot be run single-process
under `C:/anaconda` -- every test reaching `scaling_analysis.analyze` -> `_fit_power_law` ->
`np.polyfit` -> `np.linalg.lstsq` hard-aborts (`Fatal Python error: Aborted`) on that interpreter's
numpy 2.0.0 + MKL + torch-nightly stack, on `main` as well, and pinning `OMP_NUM_THREADS`/
`MKL_NUM_THREADS` does not suppress it. And `pytest-xdist` is absent from `C:/anaconda`, so
`run_cpu_tests.py` cannot run there at all.
